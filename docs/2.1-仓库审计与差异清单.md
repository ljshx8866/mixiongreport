**审计日期：**2026-10-13  
**依据：**[2.1 开发规格](人事管理2.1开发规格.md)、[1.0 收尾报告](v1.0-release-report.md)、当前工作区源码与可读取的原讨论记录。  
**阶段结论：**代码事实审计已完成；用户本轮补充确认了三方转店的身份、顺序和拒绝规则，但原讨论中其余审批和敏感资料细则仍无法取得原文，1.0 发布源码也尚无不可变标签。因此目前可实施已确认的纯工时统计与转店审批顺序、接口草案，不能据此创建生产人事表、启用敏感资料采集或正式计薪。

## 2. 已证实的数据模型与 2.1 映射

以下均取自 `database/prisma/schema.prisma` 及对应迁移，不把逻辑实体误认为已有表。

| 现有模型/表 | 已证实字段、约束或关系 | 2.1 映射与限制 |
| --- | --- | --- |
| `Region` / `regions` | `id`、`name`；与门店一对多 | 仅区域名称，没有公司、法人或人事组织层级 |
| `Store` / `stores` | 唯一 `storeCode`、唯一可空 `externalStoreCode`、`regionId` 外键、启停状态 | 可作为门店主数据；没有历史门店归属规则 |
| `User` / `users` | 唯一可空 `mobile`、`openid`、`externalUserId`、`externalUserCode`；角色 `ADMIN/REGION_MANAGER/STORE_MANAGER`；来源 `LOCAL/POS`、启停与 POS 职务名称 | 是**系统登录/权限账号**，不是人事员工档案。POS 员工数据目前用于账号同步；不能把停用账号等同离职，也不能用账号表承载薪资和证件 |
| `UserStore` / `user_stores` | `userId`、`storeId` 外键；二者组合唯一 | 表示当前可访问门店，没有生效日期或任职历史；不能作为转店事实表 |
| `StoreDailyInput` / `store_daily_inputs` | `storeId+businessDate` 唯一，`laborHours Decimal(12,2)` 是门店日汇总值；`submittedBy` 指向账号 | 不是逐员工、逐班次原始工时；2.1 不应覆盖或重算此字段，也不能从中反推出员工工时 |
| `DailyReportState` / `daily_report_states` | `storeId+businessDate` 唯一，状态 `OPEN/SUBMITTED/VERIFIED/LOCKED` | 仅经营日报状态；不可复用为薪资月审状态 |
| `AuditLog` / `audit_logs` | 操作人、实体类型/ID、动作、前后 JSON、理由、时间；实体索引 | 可借鉴审计写法；当前无敏感字段过滤、下载审计、不可篡改存储保证，人事审计需要独立约束 |
| `FillReminder*` 四表 | 门店提醒时间、收件人优先级、单日任务、发送日志；任务唯一 `configId+businessDate` | 可参考发送流程；不是员工班次版本通知，幂等键和模板须重做 |
| `ApiSyncLog` / `api_sync_logs` | `storeId+businessDate+apiType` 查询索引、状态与请求/响应 | 仅 POS 同步诊断；不承载 OCR 结果或人事审批 |

其他现有表 `product_categories`、`products`、`business_periods`、`power_calculation_configs`、`daily_sales`、`sales_periods`、`group_buy_sales`、`product_daily_sales` 仅服务经营日报；2.1 不改其业务口径。现有 Prisma 表关系和约束见 `20260928000000_init` 至 `20261008020000_product_package_flag` 九个迁移。数据库中**没有**员工任职段、入离职、转店审批、班次、原始工时、调薪、月审快照、银行卡或 OCR 实体。

## 3. 可复用能力、接口与权限差异

- `apps/api/src/auth.ts` 的 JWT 守卫每次从数据库重新加载账号与 `UserStore` 范围；`assertStoreAccess` 对经营接口做门店校验。`apps/api/src/administration.controller.ts` 的用户管理以 `ADMIN` 为主；2.1 需要新增员工本人、人事、审批当前节点、任职有效期和敏感字段级授权，不能只扩展前端菜单。
- `apps/api/src/user-sync.ts` 根据 POS 是否管理员、授权门店数映射三种角色，并同步启停。若 2.1 以同一手机号连接员工档案与登录账号，必须先设计身份核验和冲突处理；不得由 POS 每日账号同步直接改写人事任职历史。
- 现有 `/api/auth/*`、`/api/users`、`/api/auth/stores` 可作为登录和门店选择基础。日报 `/api/daily-inputs`、`/api/reports/daily`、`/api/exports/daily.xlsx` 保持兼容；新增人事路由与表，不改变 1.0 数据模型与口径。
- `apps/api/src/reminder.service.ts` 目前使用固定日报提醒模板和 `pages/input/index` 落地页。排班逐人通知必须核实微信模板、订阅授权次数、接收者绑定及失败回执；现有填报提醒配置不表示员工同意接收排班消息。
- `apps/api/src/export.controller.ts` 的直接下载适合经营日报；月度人事审核需要版本快照、导出哈希、权限校验、脱敏与下载审计。没有现成文件存储和过期清理。
- `apps/miniapp/src/utils/session.ts` 用设备本地日期决定“今天”；2.1 的昨日/明日排班与跨日归属应由服务端按门店时区确定，不依赖手机时钟。

## 4. 原讨论核验结果与待确认规则

通过 `read_thread` 可读取到原讨论用户消息：明确要求前一日排次日班、逐人通知、次日确认昨日工时、授权条件检查、不满足时店长可见，以及不足 30 分钟舍弃。用户最终说“所有已确认”。但原讨论的助手回复在可读取记录中仅是 `chatgpt-content-reference` 占位符，未包含被确认的问题和选项。**本轮用户又明确确认：三方为原店、新店、人事；按此顺序串行审批，任一方拒绝则不执行转店。**这部分规则已独立实现为纯审批顺序函数，尚未连接数据库或实际人员授权。下列具体规则仍未确认，规格中的建议表格不能替代确认：

1. 三方转店的撤回、超时和生效日规则；是否允许兼岗及跨店同日工时如何归属。
2. 用户已确认人事相关角色由后台设定；尚需确认后台配置的是角色权限、审批节点人员还是两者，以及配置权限、同岗兼任或代理、申请人回避、月审与追溯调薪的审批链。
3. 入职证件和银行卡的**逐项必填字段**、银行卡验证与本人确认方式、个人资料保存期限。OCR 服务商由用户确定为后续再接入，当前只预留供应方接口。
4. 班次跨午夜、休息扣除、补排范围、未排班出勤；微信排班模板、授权条件和发送限制。
5. 工资标准单位、月中/追溯计薪公式及正式工资导出的放行依据。已确认的 30 分钟舍弃仅为业务工时统计，不能自行升级为工资计算规则。

在这些规则获得原文或新的明确确认前，不创建需要它们定义的生产表或状态机，也不启用 OCR/银行卡生产采集与正式计薪。

## 5. 迁移、兼容、回滚与版本基线

1. **迁移路径：**先取得生产数据库可恢复备份并做恢复验证；再设计只新增表/索引的 Prisma 迁移。`prisma migrate deploy` 是前向应用，当前仓库无成套 down migration；回滚应以旧代码可继续读写 1.0 表、新人事表暂不启用为界，而非依赖危险的自动删表。
2. **身份兼容：**先建立独立员工标识，`User` 只作为可选登录关联；对 POS 用户编码、手机号重复和停用状态进行只读比对。历史门店汇总 `laborHours` 不做逐人分摊或猜测性回填。缺失的入职/任职事实标为待补录。
3. **旧接口兼容：**保留所有 1.0 路由和日报计算。新功能用独立 API、权限和前端模块接入；员工级工时不得静默覆盖门店日报人工工时。若将来需要联动，另设显式规则和回归验收。
4. **版本基线：**已将当前本地相关源码与配置的 89 个 SHA-256 值记录在 `docs/2.1-starting-workspace-manifest.sha256`，作为本轮变更对照。该清单生成于独立人事计算模块加入后，是**2.1 开工时本地工作区记录**，不是纯 1.0、生产镜像或微信线上包的校验结果。本地仓库目前只有早期提交，工作区含大量未提交的 1.0 源码、迁移及交付文件；线上小程序 1.3.20 由产品负责人确认，但缺少与 Git 提交一一对应的包证据。创建发布标签前必须筛查工作区、排除临时压缩包/凭据、核对生产镜像与线上小程序包；不能把当前旧提交直接标成 1.0。
5. **运行环境：**1.0 收尾报告已验证 Ubuntu 24.04、四容器、9 个迁移和 HTTPS。数据库自动备份/恢复演练仍未核实，且有 2 条历史 `RUNNING` 同步日志。2.1 上线前应补备份、告警、迁移演练与回滚包。

## 6. 可立即执行的确定性工作

- 已将“按员工、业务日汇总已确认原始分钟，再按每满 30 分钟计 0.5 小时”的纯函数放入 `packages/hr-engine`，测试 29/30/59/60/61 分钟与 20+20 分钟。函数输入应是**已归属同一业务日**的分钟段；它不决定跨日、跨店归属，更不计算应发工资。
- 已按本轮确认实现原店 → 新店 → 人事的纯审批进度函数；任一拒绝终止，三方通过后仅进入“待生效”，不擅自计算生效日或执行转店。
- 已在 `apps/api/src/hr/ocr-provider.ts` 预留厂商无关的识别接口和字段置信度返回类型；尚未启用上传、识别、保存或生产采集。
- 编写人事 API 的语义草案、权限验收用例和敏感字段清单；缺少审批链和采集字段前仅作为草案。
- 准备 1.0 发布源码清单、生产备份与恢复方案，待确认后再做迁移与正式页面。
