# 人事管理 2.1 入离职可见性与规格复核

复核时间：2026-10-15。依据《人事管理2.1开发规格.md》、此后确认的规则、本地源码与生产只读检查。此前《2.1 规格对照与本轮交付》将“功能代码已部署”表述得过于接近“每个终端和账号均可见、业务闭环已验收”；本记录校正该边界。

## 用户看不到入离职的原因

1. **小程序线上版本仍是 1.3.20。** 2.1.0 只是开发版，原开发包的人事工作台没有入职、离职页面或入口。现已补入两个移动页面，2.1.2 构建并由微信开发者工具 CLI 上传为开发版；没有提交审核，线上用户仍看不到。
2. **后台组件已部署，但按独立人事权限显示。** 生产前端资源中有“入职审批”“离职审批”；生产角色 `01` 拥有入职、离职等全部人事权限，角色 `02` 拥有门店发起/核验权限。生产总部管理员账号（用户 ID 1）没有人事角色授权；角色 `01` 当前授给另一位门店账号（用户 ID 9），`02` 授给用户 ID 43 的指定门店。因此管理员账号没有入离职菜单，是权限配置结果。没有擅自新增或转移敏感人事权限。
3. **失败提示不足。** 旧后台读取 `/api/hr/current-access` 失败时直接隐藏模块。现已增加明确的读取失败或未授权提示，并部署后台；员工档案的过期说明已更正。角色或门店授权仍须由有配置权限的负责人按实际职责分配。
4. **生产目前没有员工档案和入离职申请。** 只读数据库核对三项记录数均为 0；授权后列表仍会为空，需先建立员工草稿，再录入资料、提交审批。

## 与规格相比仍未完整交付或尚无验收证据

| 规格项 | 当前差距 | 处理方向 |
|---|---|---|
| 员工自助入职资料、本人的入离职状态 | 当前是门店核验和人事审批流程；小程序本人只可看排班、工时，没有本人档案及自助资料页。后续用户确认的“门店现场核验、人事看脱敏结果”已落实，但员工本人提交仍是规格差距 | 设计本人资料/申请只读或提交入口及账号与员工档案绑定流程 |
| 身份证 OCR 主要字段自动填写 | API 支持姓名、性别、民族、出生日期、地址、证件号等结构化字段；后台和小程序目前只自动填证件号并比较姓名，其余字段没有录入控件；背面签发信息也未在页面录入 | 补字段 UI、人工核对及敏感草稿保存 |
| 预留未命名入职字段 | 当前敏感草稿数据结构仅有已命名证件和银行卡字段，没有可配置扩展字段模型 | 待字段定义后设计可配置字段和版本化存储 |
| 离职最后工作日、附件及员工本人结果页 | 当前已保存生效日、原因、审批及历史，未提供独立最后工作日或附件；本人结果页缺失 | 结合业务定义补字段和权限 |
| 审计查询与完整异常工作台 | 服务端关键操作写审计，月审有待处理清单；没有统一的人事审计查询页，也没有含负责人/处理期限的独立异常队列 | 分模块补查询和处理页面 |
| 排班逐人微信消息发送 | 按用户要求留待上线后单独处理 | 保持 `HR_SCHEDULE_NOTIFY_ENABLED=false` |
| 真实业务闭环 | 员工、入离职申请均为 0；OCR 未用经授权的脱敏真实样本验收；小程序新增页面仅通过编译，尚未真机走通 | 用授权测试账号和脱敏样本做门店、人事两端 UAT |
