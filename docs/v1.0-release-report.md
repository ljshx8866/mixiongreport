## 二、系统架构与部署

| 层次 | 组件 | 作用 |
| --- | --- | --- |
| 门店端 | uni-app、Vue 3、TypeScript 编译为微信小程序 | 登录、填报、日报、历史查询、提醒处理、简报图片分享 |
| 总部端 | Vue 3、TypeScript、Vite | 经营看板、日报查询、同步审核、提醒配置、用户权限与主数据查看 |
| 服务端 | NestJS、TypeScript | 鉴权、门店隔离、POS 同步、日报装配、状态流转、Excel 导出 |
| 计算层 | `packages/report-engine` | 客单价、占比、能源与工时效率、菜品汇总、完整性与异常检查 |
| 数据层 | MySQL 8.4、Prisma | 主数据、POS 同步结果、人工数据、状态、日志与审计 |
| 接入层 | Caddy、Docker Compose | HTTPS、反向代理、容器编排 |

生产服务器为 Ubuntu 24.04，项目目录为 `/opt/restaurant-report`。运行中的服务是 `db`、`api`、`admin`、`caddy`。MySQL 不向公网开放，API 映射在服务器回环地址；公网经 Caddy 到后台，后台转发 `/api/` 请求。`https://mx.sxhhg.com.cn/` 和 `https://mixiong6.com/` 均返回 HTTP 200，TLS 验证通过。小程序生产环境的 API 地址仍为 `https://mx.sxhhg.com.cn`。

数据流为：POS API → 同步服务 → 主数据及每日销售数据 → 日报服务；门店填报单独写入人工数据；日报计算层在读取时生成 DTO，供小程序、后台及 Excel 导出使用。同步日志保存原始响应并记录成功或失败，重要人工修改及状态变更写入审计记录。

## 三、1.0 功能范围

### POS 与主数据

- 已对接真实吾享接口，按 POS 编码同步门店、分类、菜品、营业与菜品销量；分类及菜品名称随主数据同步更新。
- POS 用户、启停状态和门店管理范围可同步；本地用户仍可管理，手机号做唯一性约束。后台可手动触发主数据和用户同步。
- 菜品可区分单品与套餐；后台可筛选停用菜品和套餐。POS 同步资料以查看为主，日报显示开关及隐藏菜品归集目标为本系统配置。
- 自动同步已开启：08:30 刷新主数据和用户，09:00–23:00 每小时同步当日经营数据，次日 02:00 同步前一日数据。填报提交前还会同步该门店当日 POS 数据。

### 日报与人工填报

- `GET /api/reports/daily` 返回单店单日统一日报模型，包含销售渠道、营业时段、团购、能源、人工效率、分类销量、菜品明细、完整性状态与异常代码。
- 客单价、占比、效率等指标由后端统一计算；除零返回空值。金额汇总按分处理。毛利字段在 1.0 保留，当前无完整成本数据时返回空值。
- 入客数采用已定稿口径：POS 的“计算碗数”收入分类；套餐展开明细、名称含“半份”按 0.5、员工餐结算订单不计入客数，汇总后取整并分配到渠道和时段。销售额和菜品销量保留 POS 数据。
- 人工填报当前保留总用电、厨房用电、前厅用电、用水吨数和工时数量。提交时先完成当日 POS 同步，随后将草稿改为已提交；同步失败时保留草稿并提示重试。
- 分类和单品可分别控制是否在日报显示；隐藏单品可归集到指定的显示菜品。分类汇总及菜品明细由同一数据模型生成。
- 日报状态支持提交、审核、锁定；提供 Excel 导出及修改审计。

### 用户端与运营

- 后台按经营中心、日报作业、系统管理、个人中心分组展示；包含日报、填报、同步审核、提醒、用户权限、门店及菜品资料。
- 小程序包含首页、每日填报、日报、历史日历、个人中心、提醒，以及可转发的日报简报图片。手机号快捷登录失败时可切换账号密码登录。
- 填报提醒支持后台设置时间与人员顺位、同门店指定转派和自动顺位提醒；当日已提交则不再提醒。订阅消息点击进入填报页面。微信订阅消息实际送达还受用户订阅授权与微信平台返回结果约束。
- 门店使用说明见 `docs/门店小程序使用手册.pdf`。

## 五、交付边界与运维事项

以下事项**不改变 1.0 已完成及口径已定稿的结论**，但应在下一阶段规划或日常运维中明确负责人：

1. **版本可追溯性：**当前本地 Git 工作区有约 74 项未提交变更，仓库只有早期提交；尚未形成与生产部署、微信线上 1.3.20 一一对应的不可变 Git tag 或发布清单。API、填报、日报与后台的抽样源文件与服务器副本哈希一致；服务器上的小程序源码副本不是微信线上包的独立证明。
2. **同步日志收敛：**数据库中有 2 条历史 `RUNNING` 日志未结束。应建立超时归档、失败告警及定期巡检；这两条日志本身不等于当前同步仍在运行。
3. **备份与恢复：**本次未核实数据库自动备份、异地备份及恢复演练。上线运维方案应写明备份频率、保存周期、恢复负责人及一次实际恢复验证。
4. **任务运行方式：**POS 同步和提醒由 API 进程内定时器执行。若以后扩成多实例，应设计跨实例互斥、任务队列或独立 worker，避免重复执行。
5. **历史快照：**日报在读取时按现有主数据和显示配置生成。若未来要求已锁定日报在分类或菜品名称变更后仍保持原样，需要新增报表快照或配置版本机制。
6. **毛利与扩展报表：**完整毛利成本、库存、采购、排班、会员、财务记账、复杂 BI 和 PDF 不属于本次 1.0 已交付能力。
