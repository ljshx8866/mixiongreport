# 人事管理 2.1 阶段 1：数据库设计与迁移检查

状态：**仅在本地生成迁移，未执行在生产或测试数据库。**

## 本次新增

| 新表 | 用途与边界 |
| --- | --- |
| `hr_employees` | 独立员工身份；`user_id` 为可空且唯一的现有登录账号关联。POS 账号停用或删除不会自动代表员工离职。当前仅存显示姓名，不采集证件、银行卡或薪资。 |
| `hr_primary_appointments` | 员工主门店任职区间，日期左闭右开。旧门店到新门店可在同一天无缝衔接；任职历史不靠覆盖旧记录表达。 |
| `hr_roles`、`hr_permissions`、`hr_role_permissions` | 后台可配置的人事角色及其权限集合，独立于 1.0 的 `UserRole` 枚举。权限代码尚未定稿或预置。 |
| `hr_role_grants` | 向登录账号授予人事角色，支持全局、区域或门店范围；同一账号、角色、范围只能有一条授权。POS 的 `UserStore` 同步不会覆盖它。删除登录账号时授权随账号删除，独立员工档案及任职历史保留。 |

迁移文件：[20261014010000_hr_foundation/migration.sql](../database/prisma/migrations/20261014010000_hr_foundation/migration.sql)。它只创建新表并为新表添加外键，不修改、删除或搬迁 1.0 的业务数据。`hr_primary_appointments` 对结束日晚于开始日设数据库约束；`hr_role_grants` 对全局范围 ID 为 0、区域/门店范围 ID 大于 0 设数据库约束。

## 必须在写入接口落实的约束

- MySQL 无内置排他区间约束；主门店任职段的重叠检查必须在事务中先锁定员工行，再读取任职段、校验并写入，避免并发转店产生两条有效主归属。纯函数 `findPrimaryAppointmentOverlaps` 已实现和测试，但**不能单独替代事务约束**。
- `hr_role_grants.scope_id` 是多态范围 ID，数据库只能限制数值形态，无法同时给区域、门店建立外键。所有授权写入须按 `scope_kind` 核验目标存在且可用；删除或停用区域/门店时须处理授权。纯函数 `canAccessHrStore` 已验证禁用账号、角色、授权、缺失权限和跨店/跨区拒绝；服务端后续必须加载最新授权，不信任前端提交的角色。
- 后端现已注册 `HrAccessService`，它在每次调用时重新查询账号状态、角色权限、授权和门店区域；现有 1.0 的 ADMIN 角色、POS 门店管理范围及系统 API Key 均不会自动授权人事访问。服务尚无公开路由。`REPORT_SOURCE` 非数据库模式时人事授权直接拒绝。
- POS 账号停用再启用时，原人事授权是否恢复尚待确认。当前服务仅在账号停用期间拒绝访问，尚未修改 POS 同步逻辑；正式开放角色授予前须定稿并覆盖自动同步、手动停用和重新启用场景。
- 敏感字段、审批链、生效规则尚未定稿。现阶段没有角色配置接口、员工资料写接口、审批接口或默认管理员授权，也不将新增表接入 1.0 鉴权守卫。
- 未来删除账号前须在独立审计中保留其授权变更记录；`hr_role_grants` 是当前授权，不作为授权历史日志。
- `HrEmployee.displayName` 是基础档案字段，后续入职必填项、员工唯一编号和重复人员合并策略仍须确定；不得凭同名或手机号自动合并员工。
