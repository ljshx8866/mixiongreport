# 米熊经营系统：项目交接与可复用开发避坑指南

> 为后续新对话准备的项目上下文。整理日期：2026-11-09。生产环境信息最后一次由 Codex 实际核验：2026-11-02。新任务开始前仍要重新读取服务器状态，文档不是实时监控。

## 1. 项目是什么

这是米熊连锁门店在用的经营系统，核心是 POS 经营日报，同时包含后台与微信小程序的人事、排班、工时和通知功能。经营与人事是同一套产品：共用账号体系、门店授权范围、角色和权限目录；不要把人事做成另一套独立系统。

### 技术结构

| 模块 | 技术与入口 |
|---|---|
| API | NestJS 11、TypeScript、Prisma 6、MySQL 8.4；`apps/api` |
| 后台 | Vue 3、Vite；`apps/admin` |
| 微信小程序 | Uni-app、Vue 3，目标平台为微信小程序；`apps/miniapp` |
| 经营计算 | `packages/report-engine`，保持公式可独立测试 |
| 人事计算 | `packages/hr-engine`，处理排班、跨日工时和休息扣除等纯逻辑 |
| 数据与部署 | `database/prisma`、`compose.yaml`、`scripts/`、`deploy/systemd/` |

根目录是 npm workspaces。生产由 Docker Compose 管理 MySQL、API、后台和 Caddy；HTTPS 域名为 `mixiong6.com`，`www.mixiong6.com` 指向同一后台。后续只操作现役生产环境；历史机器信息不用于连接或发布。

## 2. 主要业务规则

### 经营日报与 POS

- POS 是销售、菜品、分类等数据的来源；本地日报以同步后的 POS 商品 ID 和本地商品关联为基础。
- POS 新增商品或分类后，先同步主数据，再同步营业数据。若商品未映射，必须定位并补齐关联，避免生成无法归属的商品销售；不要靠反复重跑一个缺少主数据的同步来修复。
- 销售口径和日报计算集中在 `report-engine`；修改分类、套餐、员工餐、入客数等口径时，用真实接口字段和测试样例验证，不在前端另算一遍。
- 已生成日报是有业务意义的快照。修改上游资料或试岗状态时，不应擅自改写已生成日报；若确实需要重算，明确影响范围并走受控流程。

### 账号、员工、角色与门店范围

- 本地权限为准，POS 同步不得覆盖本地账号权限；账号可以通过手机号关联员工资料，重复手机号应复用现有账号，避免产生重复账号。
- 经营、人事、排班使用同一个门店管理范围逻辑。多门店管理者可在相关功能内部切换门店；权限由服务端按当前用户和门店校验。
- 权限应与具体功能对应，按平台（后台/小程序）和功能层级整理；界面隐藏只是体验控制，API 仍必须校验叶子权限。
- 保存角色权限时只更新已知权限码，保留未知的未来/兼容权限；兼容迁移不能无意清空现有角色授权。
- 新增角色可由名称自动生成编号。入职可选的角色由“允许入职时分配”的配置决定，默认角色为员工。
- 员工岗位可归属多个门店；岗位可配置门店工时工资。POS 的职务/岗位标签不应冒充本地人事角色或授权信息。

### 人事与审批

- 入职录入选择岗位和账号权限；审批人核对资料并按流程审批，不替申请人重新选择这些资料。匹配到已有手机号账号时复用并更新姓名、门店范围和权限，不重复新建。
- 转店顺序为调出店申请、调入店店长审批、人事总监审批；生效后更新同一账号的门店权限，并保留任职与审批历史。
- 离职、调薪和银行卡变更应使用同一员工/账号/权限体系，失败信息应返回可操作的中文具体原因。身份证、银行卡等敏感资料必须继续使用既有服务端加密和访问审计，不写入普通日志。
- 工时更正由有权限者直接修改，不走审批；所有更正/删除都应保留版本或审计记录。

### 排班、工时与工资

- 同一员工可同一天排多个班次；冲突按实际时间区间检查。日期选择和时间编辑需要兼容微信及鸿蒙等运行环境。
- 班次模板与排班点位是独立配置；排班可给每人选点位，汇总图按员工着色，并在员工名称后显示点位与时间安排。
- 同一员工同一天的班次在列表/确认中可合并呈现；实际计算仍要保留各班次和休息段，休息时间不得计入工作工时。工时计算统一使用 `hr-engine`，不要在页面里另写算法。
- 角色可设置“参与排班”。排班专用岗位可以只显示排班，不确认工时、不计算工资。
- 员工工时以已确认的实际工时为准；填报的工时自动读取确认结果。工时统计按所选门店、人员和日期范围筛选。
- 工资由已确认工时与当日有效岗位时薪计算；时薪有效日期和按日舍入口径要覆盖测试。试岗期间工时暂不计工资，正式转入职后，试岗开始日起的已确认工时按适用岗位时薪纳入。

### 试岗

- 录入只需姓名和开始日期；试岗人员可排班并确认工时。
- 结束试岗会归档，不删除试岗人员、排班、工时或操作日志；后台「试岗管理—历史记录」可查。它不会改写已生成经营日报。
- 历史列表按试岗门店查看试岗中、已结束、已转入职及转入职后离职人员。旧删除逻辑已经彻底删除的记录无法从新历史页恢复。

### 通知与小程序首页

- 站内通知按账号保存已读/未读状态；只有当前账号确实需要的通知类型才显示授权和开关。订阅授权不能用无关流程反复打扰用户。
- 小程序常用功能应使用统一功能目录和账号级保存；新增模块时同步检查目录、权限、收藏和跳转目标。
- 页面状态和错误信息都用中文呈现，身份过期时清理会话并跳转登录。

## 3. 开发经验与常见坑

1. **先检查真实数据流，再改界面。** 503 或“加载中”可能来自 POS 主数据关联、服务端异常、权限、路由参数或平台 API 差异；用日志、接口响应和数据表确认根因，不能只加重试或延长 loading。
2. **主数据同步先于业务数据同步。** POS 商品/分类缺失会造成关联失败；POS `-400004` 通常要核对对应门店的 `ACCESSID` 与 `ACCESS_TOKEN` 配对授权，不能把凭据写入代码或小程序。
3. **日期只表示日期时不要当成 UTC 时间戳。** 业务时区是北京时间；跨日排班和结算要在统一函数里切分。前端使用 `apps/miniapp/src/utils/china-time.ts` 等既有工具，避免 `new Date('YYYY-MM-DD')` 在不同设备显示前一天。
4. **不要假设小程序就是完整浏览器。** 曾遇到 `URLSearchParams` 缺失、日期控件无显示、Canvas 初始化失败等兼容问题。优先使用微信/Uni-app 明确支持的 API；上传/保存图片要处理授权、回调与失败提示，并在开发者工具和真实手机验证。
5. **加载状态必须有收尾。** Promise 的成功、失败和超时分支都要结束 loading；错误保留接口实际原因，转换成明确中文。审批详情跳转需检查不同平台的 query 参数和页面栈。
6. **权限前后端一致。** 新页面有菜单不等于可调用接口；反过来有 API 权限也不代表入口应显示。逐个核对权限码、门店范围、页面入口、API guard 和角色默认值。
7. **业务动作优先留痕而非硬删除。** 审批、转店、离职、试岗结束和工时更正都需要状态历史/版本/审计。硬删除只用于明确授权的彻底删除，并说明受影响的数据。
8. **避免重复记录。** 补录应更新同一条业务记录并追加日志；入职与账号匹配按手机号复用；审批/通知/同步需设计幂等键或数据库唯一约束。
9. **时薪和工时不要重复计算。** 休息段、跨日边界、班次专用岗位、试岗工资和一键确认必须使用同一计算规则；给算法加边界测试，再用一组真实业务示例核对。
10. **后台多 Tab 必须由当前 Tab 驱动内容。** Tab 只改了高亮而内容仍绑定旧页面，是组件状态/路由与 `current` 未统一的典型错误；逐个点开测试每个 Tab。
11. **数据库迁移与代码发布顺序固定。** 先校验迁移、备份和恢复可用性；按项目 migration 文件名完整执行待迁移项；再生成并部署匹配的 Prisma Client。禁止在 API 启动时自动迁移，也不要从 Windows 复制 Prisma 二进制到 Linux。
12. **不要把密钥和生产数据塞进 Git。** `.env`、OpenID、手机号、身份证、银行卡、POS 凭据、OCR 密钥、数据库 dump 和发布 tar/zip 均不应上传。示例配置只放占位值。

## 4. 常用命令

```powershell
# 安装依赖和生成 Prisma Client
npm ci
npm run prisma:generate

# 全量测试/构建
npm test
npm run build

# 分模块构建
npm run build -w admin
npm run build:mp-weixin -w @restaurant/miniapp

# 小程序日期工具测试
npm run test:time -w @restaurant/miniapp
```

API 使用 Node 内置测试运行器，通常是 `node --test --test-isolation=none test/*.test.js`；测试覆盖范围、权限和关键业务边界。修改后先跑相关测试，再按影响范围跑全量测试。Windows 沙箱下偶尔会遇到子进程 `spawn EPERM`；这通常是执行环境限制，确认原因后在获准的本机终端重跑构建，不要因此修改业务代码绕过构建。
