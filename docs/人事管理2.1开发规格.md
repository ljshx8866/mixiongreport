## 1. 目标、边界与不做事项

【已确认】2.1 覆盖员工入离职、身份/OCR/银行卡、跨店与三方转店、排班与工时、业务统计、调薪与追溯、异常更正、月度审核和 Excel 导出。月度周期为自然月，次月 10 日为发薪业务节点，**系统能力截至人事审核后导出 Excel**；不在本期开发银行付款、自动打款、个税/社保申报或“审核即已发薪”的状态。

交付目标：可追踪每名员工从入职到离职的有效任职和门店归属；店长按前一日排次日班并逐人通知；次日确认昨日原始工时；月末形成可审核、可追溯的业务统计与导出。历史事实不可由后续修改覆盖。

边界原则：排班是计划，实际工时是确认事实，30 分钟折算是业务展示/统计口径，正式工资计算需要独立合规闸口。日期按门店业务时区处理，跨日班次按明确归属日规则处理；若 1.0 有既定时区和跨日口径，审计后继承并写入验收。

## 3. 员工全生命周期、OCR 与银行卡

### 3.1 入职

【已确认】支持员工入职及 OCR、银行卡资料。具体必填清单【待原文核验】。建议状态：草稿 → 待本人确认 → 待人事审核 → 在职；驳回返回待补正，取消保留记录。申请时记录拟入职日、拟归属门店、岗位、任职类型、薪资方案引用及资料版本；人事通过后按生效日建立任职段。未审核不得进入正式排班和导出。若业务允许预排班，必须单独标注，不得生成已确认工时。

OCR 仅作为录入辅助：原图/识别结果/人工修正/本人确认分别保存，标注识别来源、供应方结果号、置信度、校对人和时间；低置信度、姓名/证件号不一致进入人工复核。拒绝或失败可手工录入，不让 OCR 结果直接改写已审核资料。上传类型、大小、病毒/恶意文件检查、加密和访问期限沿用 1.0 能力或审计后补齐。

银行卡支持新增、更换、失效，记录开户人一致性及生效区间。完整卡号只在必要业务点解密或显示，常规页面掩码；不写入日志、通知或前端埋点。更换不能覆盖旧版本，应保留审核证据和历史导出快照。银行卡验证方式和是否必须本人确认【待原文核验】。

### 3.2 离职

建议状态：申请 → 审核 → 已生效；保留申请日、最后工作日、生效日、原因和附件。离职生效后禁止新排班/转店/调薪自动生效，已发生工时与历史报表仍可查。未完成的排班、工时异常、转店和月度结算在审核前列清单；不能简单级联删除。离职后的银行卡、身份原图留存/删除策略由法定保存义务、合同和企业制度决定，不能由前端“删除员工”直接物理清除。

## 4. 跨店与三方转店审批

【已确认】必须支持跨店和“三方转店审批”；具体三方身份和顺序【待原文核验】，不能将建议审批链当成已确认结论。逻辑上至少保存转出门店、转入门店、员工、拟生效日、申请理由、参与的三方、每方决定及时间。Codex 审计原对话后把准确的三方身份、先后/并行、超时和撤回规则填入流程配置与验收用例。

【技术建议】申请 → 多方待审批 → 已通过待生效 → 已生效；任一必需方拒绝则驳回。生效事务中关闭旧门店任职段并创建新段，确保任一时点单一主归属，或按已确认的兼岗规则建独立兼职关系。与在途离职、重复转店、同日调薪及已排班冲突时阻止生效并给可处理清单。历史班次与工时保持发生门店归属，不随人员现门店漂移；转店后新排班按新任职权限校验。

## 5. 排班、逐人微信通知与次日工时确认

### 5.1 排班

【已确认】默认由店长在前一天编排第二天的班。页面默认日期为“门店本地明天”，仍需允许有权限人员按已确认的补排规则调整其他日期；若未确认补排范围，暂只开放次日。排班行包含员工、门店、业务日期、计划起止时间、跨日标记、休息段/计划分钟、版本和发布状态。发布前检查员工在目标日有效在职及门店归属、时间合法、重复/重叠排班、必要资料和消息授权条件。修改已发布班次产生新版本和重新通知任务；已确认工时不被排班覆盖。

### 5.2 微信逐人通知

【已确认】排好班分别向对应员工发消息；发布时逐人检查授权条件；条件不满足者店长可查看。授权条件的精确清单（关注/绑定、订阅或模板授权、渠道配额等）【待 1.0 微信集成与原对话核验】。检查结果至少分为“可发送、未满足、发送中、成功、失败/可重试”；失败列表向该店店长展示员工、班次版本、原因代码、建议处理动作、最近尝试时间，不暴露不必要的微信标识。一个员工失败不回滚其他人的排班/通知。已发布班次保持可见，并标识该员工“未送达”。

【技术建议】以 `班次ID+版本+员工ID+消息类型` 做幂等键，事务提交后投递异步任务；发送前再次核验班次是否仍为最新版本。记录供应方回执，有限重试和死信/人工处理。授权缺失不可反复盲发；店长可在条件恢复后单人重试。收件人只能收到自己的班次，不群发个人排班。微信具体消息模板、可发送时段和授权有效性以真实接入协议为准。

### 5.3 次日确认昨日工时

【已确认】第二天由店长确认前一日工时。默认任务队列为“门店本地昨天”；对每个实际出勤记录确认实际起止、休息、原始分钟、异常原因和确认人。计划班次可作为预填，不能代替实际证据。缺勤、未排班上岗、跨日、重叠、跨店、离职边界均进入异常队列。确认后形成不可覆盖版本；修改须走第 9 节更正审批。店长超期未确认应进入催办与人事可见清单，不能静默按排班工时结算。

## 6. 工时口径与正式计薪隔离

【已确认】**按日、按人汇总后每满 30 分钟记 0.5 小时，不足 30 分钟舍弃**，用于业务统计；不得对每个班次分别舍弃后再加总，除非完整原对话明确另有口径。公式：`统计分钟 = floor(当日确认有效原始分钟 / 30) × 30`；`统计小时 = 统计分钟 / 60`。例如当日 29 分钟→0，59→30，61→60；同日两段 20+20→30。自然日归属、跨夜班次和休息扣除规则【待原文核验】。

**原始分钟保护**：保存每段实际起止、休息、来源和原始分钟；另存或实时计算日汇总原始分钟、统计分钟及舍弃分钟。报表/导出显式并列这些数值，不能删除 29 分钟或只留 0。更正后重新派生统计值并保留旧版本。跨店同日的计算范围按完整规则核验，默认先按员工全组织日合并，再按门店归属分摊需要另定，不擅自重复舍弃。

【上线合规闸口】30 分钟向下折算**不得直接作为工资扣减算法或唯一发薪依据**。正式计薪前需由用工/法务/人事确认合同、集体协议及依法制定的制度，核验当地工资与工时规则、加班及最低工资等约束，并通过书面批准的工资算法和样例。未通过时 Excel 只能标为“业务工时审核数据，非工资支付指令”，不输出按折算工时得出的应发实发工资。国家《劳动法》第 50 条规定工资按月支付、不得克扣或无故拖欠；《劳动合同法》第 35 条涉及劳动合同约定内容变更需协商一致并采用书面形式。参见 [劳动法](https://www.mohrss.gov.cn/xxgk2020/fdzdgknr/zcfg/fl/202011/t20201102_394625.html)、[劳动合同法](https://www.samr.gov.cn/zw/zfxxgk/fdzdgknr/bgt/art/2023/art_0abfdd261c03417b949df19d869add8d.html)。

## 7. 月度自然月审核、次月 10 日节点与 Excel

【已确认】结算区间为自然月 `当月1日00:00 至 次月1日00:00（左闭右开）`，次月 10 日为发薪业务节点。系统至“人事审核 Excel 导出”为止；不执行付款。建议状态：待汇总 → 店长提交 → 人事审核中 → 退回补正/审核通过 → 已导出。所有统计应以该月内已确认的有效工时和对应日期有效的任职/薪资版本为依据。

提交前拦截：未确认工时、未处理异常、未完成转店、待审批的覆盖本月调薪/追溯、关键入离职资料冲突。人事可查看每店待处理清单并退回；审核通过时冻结快照和规则版本。通过后有更正须走“重开—更正—复审—新导出版本”，旧 Excel 可追溯且标记作废，不能直接覆盖。

Excel 至少分为汇总、每日原始/统计工时、异常与更正、调薪生效段、审核元数据工作表；字段以原对话及现有导出规范核对。文件含月份、组织/门店、导出时间、操作者、审核版本、口径说明和“非付款指令”标识。银行卡若确需纳入，经权限和合规核验后放受控工作表/独立文件；默认仅掩码。下载链接短期有效、按权限校验，记录访问审计。导出内容按批准快照生成，重复下载字节一致或有可解释的元数据差异。

建议建立发薪日看板，提示次月 10 日节点及未完成审核，但不可将提醒视为支付完成，也不因系统未导出自动变更劳动报酬义务。

## 8. 月中调薪、追溯调薪与审批

【已确认】支持月中调薪和追溯调薪审批。申请保留员工、原/新标准、计薪单位、拟生效日、理由、依据附件、发起人、审批链和影响月份。原薪资版本只关闭有效期，不物理覆盖。月中多薪资段按实际日期及**独立获批的计薪公式**计算，不能用整月新标准覆盖旧段。

【技术建议】普通调薪：草稿 → 待审批 → 通过待生效 → 生效/驳回。追溯调薪额外计算影响月份和差额预览、要求更高层审批或复核（具体人选【待原文核验】）；若影响已审核或已导出月份，必须生成调整单和新审核/导出版本，不静默改旧快照。并发调薪、重叠有效期、倒填超过允许范围、跨门店薪资归属、离职后追溯均需明确冲突处理。降薪或合同约定变更须完成协商及书面证据后才可生效。

## 9. 异常、更正与审计

异常类型至少含未排班出勤、计划/实际差异、迟到早退、工时重叠、跨日归属待定、跨店同日、通知失败、资料/OCR 不一致、银行卡不一致、未确认工时、调薪冲突、月结后更正。异常可为待处理、待审批、已解决、驳回，必须有负责人和处理时限。

更正请求需明确原值、新值、原因、证据附件、影响对象/月份、申请人与审批人；批准后以新事实版本生效，旧值和审核意见长期可查。人事审核通过后的更正触发月度重开/复审。关键行为写审计：登录主体、角色/门店范围、操作、对象、旧新摘要、时间、来源、审批决定、导出/下载、消息发送及失败回执。审计日志不得包含完整身份证、银行卡或 OCR 原图，禁止普通业务角色修改/删除。

## 10. 逻辑数据模型与约束（非现有表结构）

| 逻辑实体 | 关键属性/关系 | 强约束 |
|---|---|---|
| 员工、任职段 | 员工标识、状态；门店/岗位/生效区间 | 任职历史不覆盖；主归属同一时点不冲突 |
| 入离职申请 | 员工、日期、状态、材料、审批 | 生效动作幂等；离职不得删除历史 |
| 证件/OCR 结果 | 文件引用、识别值、置信度、人工校对版本 | 访问受控；原始与修正区分 |
| 银行卡版本 | 加密账号、掩码、开户人、有效期、复核 | 明文最小使用；版本不覆盖 |
| 转店申请/审批步骤 | 转出/转入门店、员工、生效日、各方决策 | 每步唯一、终态不可重复生效 |
| 排班/排班版本 | 员工、门店、业务日、计划时间、发布版本 | 修改已发布班次生成版本 |
| 通知投递 | 班次版本、员工、授权检查、状态、回执 | 幂等键唯一；失败单人可重试 |
| 实际工时/确认版本 | 原始起止、休息、原始分钟、确认人 | 原始证据保留，更正追加版本 |
| 日统计派生 | 员工、业务日、原始/统计/舍弃分钟、规则版本 | 可重算；与原始工时核对 |
| 薪资版本/调薪申请 | 金额/单位、有效区间、生效依据、审批 | 有效区间不冲突；历史不覆盖 |
| 月度审核/快照/导出 | 自然月、范围、版本、审核链、文件哈希 | 审核后冻结；更正新版本 |
| 异常/更正/审计 | 类型、原新值、证据、审批、操作者 | 审计不可由业务操作删除 |

数据库实现以审计后的 1.0 模型为准。金额用精确十进制；时间点与业务日期分开；敏感字段加密和密钥管理沿用现有安全体系。对员工+日、员工+任职有效期、审批任务、投递幂等键、月度审核版本建立查询/唯一约束，具体索引依真实查询计划确定。迁移脚本可重复/可回滚并有备份验证；对历史数据只做可解释的映射和缺失标记。

## 11. API、页面与后台任务契约（建议，沿用 1.0 路由风格）

以下为**语义契约**，路径名仅示例，Codex 应适配 1.0 API 命名与鉴权。写接口接受幂等键或版本号，校验权限与状态并返回明确错误代码；列表支持门店/日期/状态筛选及分页，敏感字段默认脱敏。

| 资源/操作 | 示例语义接口 | 主要校验/返回 |
|---|---|---|
| 员工入职/离职 | `POST /employees/onboarding`、`POST /employees/{id}/offboarding` | 任职有效期、资料完整性、审批状态 |
| OCR/银行卡 | `POST /employees/{id}/ocr-jobs`、`POST /employees/{id}/bank-accounts` | 文件授权、人工确认、掩码返回 |
| 转店 | `POST /transfers`、`POST /transfers/{id}/decisions` | 三方当前节点、冲突、生效日 |
| 排班 | `GET/PUT /stores/{id}/schedules?date=`、`POST .../publish` | 前日默认、版本冲突、员工资格 |
| 通知 | `GET /stores/{id}/notification-failures`、`POST /deliveries/{id}/retry` | 本店可见、授权重检、幂等 |
| 工时 | `GET /stores/{id}/timesheets?date=`、`POST /timesheets/{id}/confirm` | 昨日任务、原始分钟、异常 |
| 更正 | `POST /corrections`、`POST /corrections/{id}/decisions` | 原新值、证据、月结影响 |
| 调薪 | `POST /salary-changes`、`POST /salary-changes/{id}/decisions` | 生效段、追溯影响、回避 |
| 月审/导出 | `POST /monthly-reviews/{month}/submit|approve|reopen|exports` | 完整性门禁、版本快照、审计 |

页面/入口：员工自助资料与本人班次工时；店长“明日排班”“通知失败”“昨日工时确认”“异常处理”；人事“入离职审核”“转店审批”“调薪/追溯”“月度审核与导出”；受控审计查询。每页展示状态、下一步操作者、异常原因、更新时间和有效日期。移动端/网页端形态以 1.0 实际工程为准。

后台任务：每日按门店时区生成昨日待确认任务及催办；排班发布后逐人授权检查与微信投递；转店/调薪到期生效；月末汇总与差异校验；导出异步生成和过期清理。每项任务具备可重试、幂等、失败告警、人工补偿及观测指标，不能因单人失败阻断整店。

| 闸口 | 放行证据 | 未通过时系统行为 |
|---|---|---|
| 原始工时与 30 分钟统计隔离 | 用工/人事/法务签字的口径说明、样例及回归用例 | 允许业务统计；禁止将折算值作为正式工资扣减依据 |

## 13. 验收测试清单

1. **权限**：店长不能读取其他店的员工银行卡/通知失败；本人只见本人；审批人不得审批自己的更正；更换门店后历史归属不漂移。
2. **入离职/OCR**：低置信度人工复核、识别错误纠正、重复员工冲突、银行卡更换和掩码、离职后保留历史工时。
3. **转店**：三方各节点批准/拒绝/撤回、重复提交、生效日冲突、跨月及同日薪资变更、并发审批只生效一次。
4. **排班通知**：前一日默认日期；发布逐人发送；一人无授权时其他人成功；失败列表本店可见；条件恢复重试；修改班次只发最新版本。
5. **工时统计**：29/30/59/60/61 分钟边界，同日 20+20，跨午夜、休息扣除、跨店同日、计划与实际差异；原始分钟及舍弃分钟始终可追溯。
6. **调薪**：月中生效按分段核对、追溯影响已导出月份、降薪书面依据门禁、重叠生效区间拒绝。
7. **月审**：未确认工时/未决异常阻止审核；自然月边界；退回补正；审核后更正触发新版本；Excel 字段、权限、脱敏、哈希与重复下载。
8. **可靠性**：异步消息重复投递、接口重试、任务中断恢复、迁移回滚与旧数据兼容；生产相近数据量下分页、汇总和导出性能。

测试数据不得使用真实身份证、银行卡和微信标识。正式验收需用脱敏样本及审批的端到端 UAT 脚本，覆盖门店和人事两类人员。
